# 混合分辨率启动修复计划

## 目标

修复Windows与Pi分别使用1920×1200、1920×1080时无法完成启动握手的问题。两端保持各自当前输出尺寸，完成自动发现、双向标定和文件交付。

## 已定位事实

`newtest_1/result.json`记录启动协商超时；`startup/progress.json`为round=0、selected_modes=null。Windows输出1200p，持续收到Pi的HELLO，尚未收到CAPS。

`automatic.startup`按本机显示尺寸生成控制图；初始接收仍使用配置中的1080p。采集尺寸的重新确认发生在选档之后。`core/control.decode`要求控制框宽高比接近固定值；软件复现中，原生1080p和1200p均可识别，将1200p图缩为1080p则识别失败。

本次Pi的实际采集尺寸和画面尚待读取。根因排查集中在选档前的接收路径。

## 第一步：取得失败画面

执行agent读取Pi对应会话日志和当前部署版本，用Windows1200p、Pi1080p启动一次短连接。在Pi首次接收位置保存一张实际控制图，记录输入信号、请求采集尺寸、实际图像尺寸及decode结果。

对照Windows的启动日志，确定画面是被压缩、裁切、黑屏，还是原生1200p。沿用现有采集和日志接口，只补定位所需的这一张图及结果。

交付：`runs/mixed-fix-新编号/diagnosis.md`，写明实际画面、失败位置和选定修复方案。

## 第二步：直接修正启动接收

修改入口：

- `automatic.py`：选档前的接收初始化与`_receive`。
- `backends/camera.py`、`discovery.py`：采集模式读取及应用。
- `core/control.py`：仅在实拍证明控制框被缩放时调整识别。

启动接收独立于本机发送尺寸。优先读取采集端实际信号对应模式；设备接口仅提供输出模式时，在1080p与1200p中依次尝试，识别到有效HELLO后继续现有能力交换。选档后按本方向协商尺寸重开采集，进入原有标定与业务流程。

若实际控制图完整但被非等比缩放，使用已定位矩形分别归一化横纵坐标，恢复固定控制网格；内容识别继续使用现有RS和CRC。若采集为黑屏或裁切，修正采集模式选择。

保留现有ModeSession及数据编解码接口，统一修改一处启动采集逻辑。直接实现两种尺寸的处理流程，字段与错误处理各由所属接口负责。

交付：代码修复和针对性测试。测试覆盖原生双尺寸控制图、实际故障形态及初始接收模式选择，并通过当前软件测试。

## 第三步：实机验收与交付

两端部署相同修复版本，分别执行：

| 场景 | Windows输出 | Pi输出 |
|---|---|---|
| A | 1920×1200 | 1920×1080 |
| B | 1920×1080 | 1920×1200 |
| C | 1920×1080 | 1920×1080 |

每个场景各端发送一个约3MB文件，使业务跨越多个分片。使用180秒业务时长，沿用当前独立启动时限。

每轮记录：初始显示尺寸、初始实际采集尺寸、选定的TX/RX尺寸、双方result、源文件与接收文件SHA。

完成标准：

- A/B均从当前不同尺寸自动完成HELLO、CAPS、标定和READY。
- 每端TX尺寸对应本端输出，RX尺寸对应对端输出。
- 三个场景双向交付完成，接收SHA与对应源文件一致。

交付：同一run目录中的`REPORT.md`，包含三行验收结果及证据路径；更新`docs/交接/当前进度.md`和使用说明中的相关说明；提交本地Git。

## 用户如何开始

1. 保持两端已登录桌面、双向HDMI/USB接线和远程连接可用。
2. 将本计划交给执行agent，工作目录设为`/mnt/hgfs/VMwareShare/visual-link`。
3. agent负责读取失败证据、修改代码、部署及切换三组测试模式。首次按场景A设置，全部完成后保持两端1080p。
4. 若桌面接口需要本机点击确认，agent给出对应设备上的具体操作。

执行提示词：

> 按docs/混合分辨率修复计划.md完成修复。先取得Pi实际失败画面，再修改启动接收路径，最后验证两个混合方向和1080p基线。复用现有模块和脚本，交付结果报告并提交本地Git。
