# 启动分辨率与60秒传输失败修复

## 原因

用户失败会话：Windows `runs/web-20261112-110333-205c00`，Pi `web-20261112-110334-9ea655`。原始两端证据已保存在`runs/fix-20261112-05/original-windows`与`original-pi`。

原选档规则从所有声明支持的模式中优先最大尺寸，默认候选含1080p、1200p，因此两端当前为1080p时也会切换到1200p。此次1200p实际采集、零错误标定和最终配置均成功。

直接失败原因是计时：`bootstrap.exchange`从60秒中扣除了自动启动耗时。Windows启动控制日志跨度约33.44秒，后续业务控制日志约26.38秒，直到截止前才完成READY。两端最终均为`connection_ready=true`，发送尝试`attempts={}`，没有发送第一片。此前较长时间的短文件验收没有覆盖这个60秒场景。

## 修改

- `automatic.capabilities`：当前显示尺寸属于候选时，只声明不大于当前尺寸的发送模式，继续允许降档；采集候选保持完整。默认两端1080p保持1080p。当前1200p仍可使用1200p；显式将候选限制为1200p仍允许切换。
- `bootstrap.exchange`：自动启动与后续传输阶段分别使用指定时长，删除扣减后续时长的逻辑。Windows子进程、任务和等待截止时间同步按两个阶段计入。
- 页面将时间标为“传输阶段 / 秒”，注明启动协商单独计时；使用说明、README、运行原理和协议同步更新。

修改集中在选档与计时，未增加异常兜底或重试层。

## 验证

31项unittest通过，新增当前1080p不升档、双向尺寸独立、显式1200p候选和启动不侵占后续时长的回归。依赖、Python AST及diff检查通过。日志：`runs/fix-20261112-05/tests.log`、`verification.log`。

两端更新后，从真实页面输入60秒启动，使用生成文件：Windows 4,257,243字节（与失败时文件等大），Pi 4,000,000字节。双方从1080p启动并保持1080p，模式报告`changed=false`，实际采集1920×1080，标定零符号错误；双向跨片交付、FINISH和回执全部完成，零重传。独立重读两端`received.bin`比对对端源文件SHA，通过。

证据：`runs/fix-20261112-05/summary.json`与`summarize.py`；页面检查`page-check.json`；截图`windows-page.png/pi-page.png`；Windows结果`transfer-windows/result.json`、Pi结果`pi-collected/transfer-pi/result.json`；全部文件SHA清单`manifest.json`。SSH仅用于部署、页面访问和回收，文件通过HDMI/USB传输。

复测使用隔离页面端口8766，验收结束已关闭；用户页面仍使用原8765。两端程序已更新，刷新页面并使用新输出目录即可重新启动；指定60秒时还需另计启动选档及设备初始化时间。
